# Day 22: Mini project — an OpenAI-style streaming server with continuous batching

Review mini project for chapters 1-4: a FastAPI server that streams tokens
over SSE from an OpenAI-style `/v1/completions` endpoint.

This day was built differently: **I was the architect.** I made every design
decision step by step, and Claude wrote the code, questioned my choices and
tested each step. The decision log below records what I chose and why.

We went past the original plan: besides streaming, the server does
**continuous batching** (the core idea behind vLLM, chapters 4.3 and 5).

## What we built

`server.py` runs `distilgpt2` on the Mac GPU (MPS) behind one endpoint:

```
POST /v1/completions
{"prompt": "The cat sat on the", "max_tokens": 16, "stream": true}
```

```
client                       request handler (async)           engine thread
  │  POST /v1/completions        │                                  │
  │ ───────────────────────────▶ │ check the request                 │
  │                              │ join the waiting line ──────────▶ │ every round:
  │                              │                                  │  1. drop finished / disconnected users
  │                              │                                  │  2. seat waiting users (max 30), prefill them
  │  data: {... " floor" ...}    │ ◀──── one token per round ────── │  3. one decode step for everyone seated
  │ ◀─────────────────────────── │                                  │  4. send each user their token
  │  data: {... finish_reason}   │                                  │
  │  data: [DONE]                │                                  │
```

The 9 commits follow the build order:

1. a first FastAPI server on port 8080
2. the OpenAI completions format, real token counts, `max_tokens`
3. reject empty prompts and requests over the 1024-token context
4. answers generated by distilgpt2
5. sampling defaults and a welcome reply for blank prompts
6. the welcome reply cut to `max_tokens`
7. SSE streaming with async generation
8. `usage` only in the last stream message
9. continuous batching on the Mac GPU, and stop on disconnect

## How to run it

```
python3 day-22/server.py
```

The first start downloads nothing new (distilgpt2 is cached from day 1). Then,
in a second terminal:

```
curl -N -X POST localhost:8080/v1/completions -H "Content-Type: application/json" \
     -d '{"prompt": "The cat sat on the", "max_tokens": 5}'
```

`-N` tells curl to print each message as it arrives. Add `"stream": false` to
get one JSON answer instead. `localhost:8080/docs` opens a page where you can
try the endpoint in the browser. Stop the server with Ctrl+C.

A streamed answer looks like this:

```
data: {"id": "cmpl-84b0...", "object": "text_completion", ..., "choices": [{"index": 0, "text": " couch", "finish_reason": null}], "usage": null}

data: {"id": "cmpl-84b0...", ..., "choices": [{"index": 0, "text": " with", "finish_reason": null}], "usage": null}

...

data: {"id": "cmpl-84b0...", ..., "choices": [{"index": 0, "text": "", "finish_reason": "length"}], "usage": {"prompt_tokens": 5, "completion_tokens": 5, "total_tokens": 10}}

data: [DONE]
```

## Decision log

| # | Question | My decision | Why, and what it changed |
|---|---|---|---|
| 1 | What to build with | FastAPI + uvicorn, port 8080 | uvicorn is the server (listens on the port); FastAPI is the app (decides what each path answers) |
| 2 | Method and path | `POST`, first `/v1/chat/{id}`, then **`/v1/completions`** | The user always sends a prompt, so POST. The path changed to OpenAI's exactly, so OpenAI-style clients can use it. OpenAI's path has no id, so the **server** makes a new id per answer, like a receipt number |
| 3 | Remember conversations? | **No memory** | Like OpenAI, the server is stateless: for a follow-up, the client sends the whole conversation again. Nothing to store, nothing lost on restart |
| 4 | Token counts in `usage` | Real tokens, from distilgpt2's tokenizer | Words are not tokens: "Aparajith" is 4 tokens (`A`, `par`, `aj`, `ith`) |
| 5 | `max_tokens` | Optional, default **16** (OpenAI's default), at least 1 | `max_tokens: 0` gets a `422` from FastAPI automatically |
| 6 | Too long a request | **Reject with `400`** if prompt + `max_tokens` > 1024 | Checked **before** the model runs, so it fails in under 1 ms. distilgpt2 can only see 1024 tokens in total |
| 7 | Empty prompt | `""` is rejected (`422`) | |
| 8 | Prompt of only spaces | Reply **"hi! welcome"**, streamed like a model answer and cut to `max_tokens` | One uniform UI. The welcome ends with the end token, so it counts as 4 tokens |
| 9 | Sampling | Fixed on the server: **temperature 0.7, top_k 10** | Greedy (temperature 0) looped ("The United States was the only country..." again and again). 0.7 keeps likely words but adds enough randomness to break loops. I first said top_p 10, but top_p is a fraction (0-1); keeping the 10 likeliest tokens is top_k |
| 10 | Client sends `temperature` anyway | **Ignore it silently** | FastAPI drops unknown fields by itself |
| 11 | Stream or not | Per request, **default `stream: true`** | Streaming improves **TTFT**: the user reads the first words while the rest is generated. Note: OpenAI's default is false, so the OpenAI library's non-streaming calls would get SSE and break |
| 12 | What each message holds | A **full OpenAI object** per token, `data: [DONE]` at the end | Same shape as OpenAI's stream |
| 13 | Live token counter | First in every message, then **only in the last message** | A 6-character token was sent in a ~300-byte message; OpenAI also sends `usage` only at the end |
| 14 | Blocking vs async | **Everything async** | One event loop is like one waiter. If the waiter cooked (`generate()`), every other table would wait. The model runs on its own thread instead |
| 15 | Client disconnects | **Stop generating** | I first said keep finishing so they have it next time, but with no memory (decision 3) the answer would be thrown away |
| 16 | Many users | **Continuous batching**, max **30** users per round, on the **Mac GPU** | Chosen from a measurement (see Results). Users join and leave at every round, so no seat stays empty |
| 17 | User 31 arrives | **Waiting line** | They join the first free seat instead of getting an error |
| 18 | When new users get their prefill | **Seat everyone waiting at the start of each round** | Fast TTFT for new users; seated users lose one round per arrival, which is cheap for a small model |

## What we learned

### HTTP and FastAPI

- A **server** waits on a **port**; a **client** sends a **request** (method,
  path, JSON body) and gets a **response** with a **status code**: `200` OK,
  `400` bad request (our context check), `405` wrong method, `422` the body has
  the wrong shape.
- A **Pydantic model** (`CompletionRequest`) lists the fields a request must
  have. FastAPI checks every request against it, so missing prompts and
  `max_tokens: 0` are rejected without any code of ours.

### The OpenAI format

Everyone speaks it (vLLM, SGLang, Ollama, hosted providers), so matching it
means existing apps work with our server by changing one URL. The response has
`id`, `object`, `created`, `model`, `choices` (`text`, `finish_reason`) and
`usage`. `finish_reason` is `"stop"` if the model ended with its end token and
`"length"` if it hit `max_tokens`.

### SSE streaming

Server-Sent Events keep one HTTP response open and send messages through it,
each one `data: ...` plus a blank line, ending with `data: [DONE]`. Tokens only
flow one way, so this is enough; WebSockets are not needed.

### Async: the waiter and the kitchen

- The **event loop** is one waiter serving many tables. Every request handler is
  `async`, so while one waits for a token, the waiter serves someone else.
- `generate()` and the model's forward pass **block**. They run on a separate
  **thread** (the kitchen), and tokens come back through an **`asyncio.Queue`**
  (the hand-off window), using `call_soon_threadsafe` because the two sides
  live on different threads.

### Continuous batching

- **Static batching:** a group starts together and every seat stays taken until
  the longest answer is done. Short answers leave empty seats, and newcomers
  wait outside.
- **Continuous batching:** at every round, finished users leave and waiting users
  join. This is what vLLM does.
- Each user has their **own KV cache** of their own length. To run one step for
  everyone, the engine **left-pads** every cache to the longest one, marks the
  padding with an attention mask of 0, gives each user their own position
  number, runs one step, and cuts the padding off again.
- **Left** padding, because the model generates at the **end**: the newest token
  of every user must line up in the last column.

### Text from tokens

Each round decodes the user's whole answer so far and sends only the new part.
Decoding token by token could split a character made of several tokens (like
an emoji) and send `�`; when the text ends in `�`, we wait for the next token.

## Results (Apple M4, 16 GB)

### How many users the Mac can serve (raw model, 128 tokens of context each)

```
          ----------- CPU -----------      ------- Mac GPU (MPS) -------
batch   step ms  total tok/s  per user    step ms  total tok/s  per user
    1      6.4         156        156        6.3         158        158
    2      9.3         214        107        6.5         305        153
    4      9.7         411        103        7.1         564        141
    8     12.4         647         81        8.3         965        121
   16     16.2         987         62       12.5        1277         80
   32     24.8        1293         40       17.3        1852         58
   64     39.9        1604         25       76.2         840         13
```

- 32 users on the Mac GPU take only about 3x longer per step than 1 user, so
  total throughput is about **12x** higher. Each user gets slower (158 → 58
  tok/s), still faster than anyone reads.
- At 64 the Mac GPU falls apart (840 tok/s). Hence the maximum of 30.
- Memory is not the limit: distilgpt2's KV cache is about 36 KB per token, so
  even a full 1024-token user needs about 38 MB.
- The first version of this test kept the scores for every vocabulary word at
  every prompt position: 256 × 128 × 50,257 × 4 bytes ≈ 6.6 GB. The Mac ran out
  of memory and froze. Keeping only the last position fixed it.

### Correctness of batching

With sampling switched to "always the likeliest token", 4 prompts of different
lengths batched together gave **exactly the same tokens** as running each one
alone. The padding does not change the answers.

### Two users, one thread each (before batching)

User A asked for 1000 tokens; user B sent `"the cat sat"` one second later. B's
first token came 0.02 s after asking and B finished in 0.17 s (0.11 s alone),
while A was still generating. Async works.

### Disconnect

A user asked for 900 tokens and left after 5. Their seat was freed and
generation stopped at 6 tokens.

### Throughput with batching (each user asks for 100 tokens)

| Users | Total tok/s | Avg TTFT | Per-user tok/s |
|---|---|---|---|
| 1 | 60 | 126 ms | 65 |
| 10 | 186 | 57 ms | 19 |
| 30 | **444** | 151 ms | 16 |
| 60 | 176 | **10.6 s** | 7 |

- 1 → 30 users: total throughput up about **7x**.
- Our engine reaches only 444 of the raw 1,852 tok/s. The big cost is copying
  every user's KV cache into a padded batch tensor and back, every round. Real
  engines avoid this with **PagedAttention** (chapter 5): the cache lives in
  fixed blocks and is never copied.
- 60 users: users 31-60 wait in line, so the average TTFT jumps to 10.6 s. The
  total also dropped to 176 instead of staying near 444, which is not explained
  yet.

## Caveats

- distilgpt2 is a tiny model, so its answers are often nonsense and repeat.
- Prefill runs one new user at a time.
- The padded batch is rebuilt every round, which costs more as answers grow.
- The waiting line has no limit and no timeout.
- `stream: false` requests cannot be cancelled by disconnecting.
- Load tests ran the client on the same Mac as the server.

## Things to try

1. Find out why 60 users gave less total throughput than 30.
2. Prefill all new arrivals in one batch instead of one at a time.
3. Keep one batch cache and only rebuild it when someone joins or leaves.
4. Call the server with the official `openai` Python library
   (`base_url="http://localhost:8080/v1"`) and see what breaks with
   `stream: true` as the default.
5. Add a limit to the waiting line and return `503` when it is full.
